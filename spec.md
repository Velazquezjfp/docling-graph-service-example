Technical Architecture & Specification: Docling Ingestion & Graph Service1. System Overview & ArchitectureThe service is a stateless document ingestion and knowledge extraction microservice running in Docker. It unifies layout analysis, OCR, visual reasoning, structural chunking, ontology-driven knowledge graph generation, and vector embeddings into a single cohesive pipeline while isolating compute-heavy model inference across remote or local OpenAI-compatible endpoints.+-----------------------------------------------------------------------------------+

Core Architecture PrinciplesDecoupled Model Inference: High-parameter models (LLMs, VLMs, Embeddings) run externally (via vLLM, TEI, or local Ollama). The ingestion container acts strictly as a parser, orchestrator, and metadata enricher.Unified Extraction Pipeline: A single input document yields three synchronized representations: enriched Markdown, hierarchical vector chunks, and an ontology-grounded knowledge graph.Structural Provenance Preservation: Every extracted chunk and graph node maintains bi-directional traceability back to the source document's Document Object Model (DOM) path, heading breadcrumbs, physical page number, and bounding box coordinates.2. Hierarchical Chunking & Provenance EngineStandard chunkers discard layout context. This service utilizes Docling's HybridChunker combined with custom DOM traversal to enrich every chunk and extracted graph node with complete structural hierarchy.1. Document Tree TraversalAs Docling parses the document into its internal abstract representation (JSON/DOM), every section heading ($H_1, H_2, H_3, \dots, H_n$) is indexed into a path array.Each element maintains a unique JSON Pointer / DOM Path (e.g., #/body/section[1]/subsection[0]/paragraph[3]).2. Chunk Metadata EnrichmentEach chunk emitted by the service contains:heading_breadcrumb: An ordered list of ancestral headings establishing context (e.g., ["System Architecture", "2. Data Ingestion", "2.1 OCR Motor"]).heading_level: Depth of the deepest parent heading.dom_path: Pointer to the element within the parsed document tree.page_index: Zero-indexed page location.bounding_boxes: Array of normalized or pixel coordinates [left, top, right, bottom] indicating where the text resides visually.3. Graph Node GroundingWhen docling-graph parses entities and relations based on the user-supplied JSON ontology:Each generated Node inherits the source_chunk_id, heading_breadcrumb, page_index, and bounding_box of the chunk where the entity was identified.Each generated Edge stores references to the source chunk supporting the relationship claim.4. Service Interface & I/O SpecificationsThe microservice exposes two primary HTTP endpoints:Endpoint: GET /v1/capabilitiesEnables upstream clients to discover active backend engines and model mappings before dispatching workloads.Response Payload:Active OCR engines (e.g., ["easyocr"]).Supported document formats (pdf, docx, pptx, html, asciidoc, md).Configured active models (LLM, VLM, Embeddings) and their target host endpoints.Active chunking algorithm and default token boundary settings.Endpoint: POST /v1/processMain entry point for document ingestion, parsing, and extraction.Input Parameters:document.name: Filename string.document.format: Document MIME or extension type.document.base64_content: Raw document content encoded in base64.pipeline_config (Optional): Runtime overrides for OCR language selection, OCR enable/disable toggle, PDF parser backend (pypdf vs. default), VLM figure enrichment toggle, and chunk token limits.ontology_graph (Optional): Dynamic JSON schema defining target entity classes, attributes, and allowed relationship types for docling-graph.Desired Output Structure:markdown: Clean Markdown text of the document, including VLM-generated visual descriptions for diagrams, charts, and embedded images.chunks: Array of layout-aware text chunks, each containing the chunk text, vector embedding array (e.g., 1024 dimensions), and hierarchical tree provenance (breadcrumbs, DOM path, page number, bounding boxes).graph: Extracted knowledge graph containing typed nodes (with attributes and layout provenance) and directed edges (with relationship labels and chunk grounding).5. Deployment & Containerization StrategyThe container lifecycle is split to support both local development and air-gapped/enterprise internal networks.Dual Container StrategyLocal Build Profile:Pulls public base images from public Docker registries.Resolves Python packages and system dependencies directly from public PyPI and Ubuntu mirrors.Default routing targets host-level Ollama instances via internal bridge networking (host.docker.internal).Enterprise / Remote Profile (Strive / Artifactory):Uses base images sourced from internal hardened registry mirrors.Enforces pip installations through private enterprise package repositories (e.g., Strive / Artifactory index URLs and trusted hosts).Routes model calls to high-concurrency remote vLLM and Text Embeddings Inference (TEI) clusters.6. Operational & Performance ConsiderationsDecoupled Memory Footprint: Because LLM/VLM runtimes are externalized, the container footprint remains low (~2–4 GB memory), avoiding CUDA Out-of-Memory (OOM) locks between PyTorch and vLLM KV-cache allocations.OCR Optimization: EasyOCR runs locally within the container. To prevent CPU starvation and event-loop blocking in async frameworks (e.g., FastAPI), OCR workloads must run in isolated thread/process pools with defined thread limits.Batch Embedding Efficiency: Extracted document chunks are bundled into a single batch request to the remote embedding endpoint rather than single-chunk serial requests, minimizing HTTP overhead.Graceful Degradation: If the remote VLM or graph extraction times out or encounters invalid schema outputs, the service gracefully falls back to returning standard Docling Markdown and layout chunks without failing the entire ingestion request.
